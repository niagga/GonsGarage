  "content": "# Exploration: Cloudware fiscal integration foundation\n\n## Outcome\n\nGonsGarage can add fiscal issuance without replacing its current customer-invoice API, but the current `Invoice` row cannot itself become the fiscal record. Keep it as the mutable operational draft/customer-workflow aggregate and introduce a separate, immutable fiscalization aggregate plus a provider-neutral gateway, a PostgreSQL transactional outbox, provider connection records, and protected PDF artifacts.\n\nThe safest first delivery is a mock-provider vertical slice. It can validate the domain states, idempotency, worker/reconciliation behavior, authorization, and transparent UI before Cloudware credentials exist. Cloudware endpoint, OAuth, idempotency, document-type, cancellation, and PDF details remain intentionally unasserted here and must come from the separate official-evidence research phase.\n\n## Confirmed boundaries\n\n- GonsGarage owns operational invoice drafts and customer workflow.\n- Cloudware is the first provider/authority for finalized fiscal documents.\n- Provider access is behind a replaceable, provider-neutral gateway.\n- Operators issue and inspect documents in GonsGarage rather than using Cloudware's operational UI.\n- There is no automatic cross-provider failover.\n- Existing `/api/v1/invoices` and `/api/v1/invoices/me` contracts remain compatible.\n- Existing or legacy invoices are never selected for fiscalization automatically.\n- This change is planning-only; no implementation, commit, or pull request is part of this exploration.\n\n## Current emitted-invoice map\n\n| Layer | Current implementation | Constraint exposed by fiscal integration |\n|---|---|---|\n| Domain | `backend/internal/domain/invoice.go` has `ID`, `CustomerID`, `Amount float64`, free-form `Status`, `Notes`, and timestamps. | It has no line items, currency, taxes, fiscal identity, invoice date/series/number, provider reference, or immutable customer/issuer snapshot. `float64` is unsuitable as the canonical fiscal money representation. |\n| Service | `backend/internal/service/invoice/invoice_service.go` performs staff create/list/delete and client own-only read/notes update. | Creation is currently a single synchronous DB write. There is no finalize/issue transition, transaction boundary spanning an outbox, or immutable state after issuance. |\n| Repository | `backend/internal/repository/postgres/invoice_repository.go` provides GORM CRUD, customer/staff lists, and physical delete. | A finalized fiscal document must not be deleted or materially rewritten just because its operational invoice is changed or deleted. |\n| HTTP | `backend/internal/handler/invoice_handler.go` exposes the current DTO and request shapes. | Compatibility requires retaining current paths, methods, authorization, envelope, field names, timestamp format, and client notes-only behavior. |\n| Routes/RBAC | `backend/cmd/api/main.go` registers `/api/v1/invoices`; `/me` is authenticated client-only by service, staff collection mutations use `RequireWorkshopStaff`, and detail GET/PATCH use service authorization. | Fiscal actions need explicit route and service authorization; they must not weaken own-only client access or existing staff-trio access. |\n| Staff UI | `/accounting/issued-invoices` lists, creates, edits, and deletes current invoices. Creation asks only for customer UUID, amount, status, and notes. | Fiscal readiness needs structured data and a visible issue/retry state without sending operators to a provider dashboard. |\n| Client UI | `/my-invoices` and `/my-invoices/[id]` list/read current invoices and let the client edit notes. | Fiscal status and PDF download can be additive, but notes editing and current list/detail behavior must continue. |\n| Frontend API/types | `issued-invoice.service.ts` uses existing routes; `IssuedInvoice` mirrors the seven-field response. | Existing service methods and required fields should not be renamed or repurposed. New fiscal operations should be additive. |\n| Tests | Service tests lock own-only access, notes-only client mutation, staff CRUD, and default `open`; handler tests lock `/invoices/me`, detail access, and RBAC; frontend tests lock route calls and current UI flows. | These are regression contracts, not tests to rewrite around a new meaning of `status`. Add fiscal tests alongside them. |\n| Schema lifecycle | Startup uses GORM `AutoMigrate`; numbered SQL migrations exist, but there is no explicit numbered migration for `invoices`. | Fiscal tables and constraints need an explicit, reviewable migration. Startup currently continues after individual `AutoMigrate` errors, which is unsafe for required fiscal infrastructure. |\n| Runtime | Production compose has one API process, PostgreSQL, and Redis. The Redis queue repository is an unimplemented stub. | Do not base delivery guarantees on the current Redis queue. PostgreSQL is the available durable coordination point. |\n\n## Compatibility contract to preserve\n\n### Existing HTTP behavior\n\nThe following must remain valid:\n\n- `GET /api/v1/invoices?limit=&offset=` for staff returns `{ \"items\": [...], \"total\": number }`.\n- `POST /api/v1/invoices` for staff accepts `customerId`, `amount`, optional `status`, and optional `notes`; it returns the current invoice representation with HTTP 201.\n- `GET /api/v1/invoices/me?limit=&offset=` remains the own-only client list with the same envelope.\n- `GET /api/v1/invoices/:id` remains available to staff and to the owning client.\n- `PATCH /api/v1/invoices/:id` continues to allow client notes while silently preventing client changes to amount/status; staff can change amount/status/notes.\n- `DELETE /api/v1/invoices/:id` remains a staff endpoint for operational invoices where deletion is still legally and operationally allowed.\n- The existing response fields remain: `id`, `customerId`, `amount`, `status`, `notes`, `createdAt`, `updatedAt`; timestamps remain RFC 3339 strings.\n- Existing pagination defaults/maxima and staff/client role semantics remain unchanged.\n\n### Compatibility implications\n\n1. Do not reinterpret the existing free-form `Invoice.Status` as the fiscal lifecycle. Add a separate fiscal summary/state.\n2. Prefer additive nested endpoints such as `/api/v1/invoices/:id/fiscalization` and `/api/v1/invoices/:id/fiscal-artifacts/...` over changing existing mutation semantics implicitly.\n3. If fiscal summary fields are added to existing responses, make them optional/additive and retain the original fields. A separate summary endpoint is lower contract risk for the first slice.\n4. Preserve `Amount float64` at the legacy API boundary, but convert validated input into decimal/minor-unit values for the fiscal snapshot. Never derive tax totals through binary floating-point arithmetic.\n5. Once issuance starts, material fiscal fields must be frozen in the fiscal snapshot. Whether the operational invoice may still change is a product decision; it must never mutate an already-issued fiscal document.\n6. Physical deletion cannot apply to an issued fiscal record. Keep the current DELETE behavior for non-fiscalized/legacy drafts, and define an explicit conflict or archival behavior for linked fiscal records.\n\n## Recommended bounded architecture\n\n```text\nexisting Invoice (mutable operational record)\n        |\n        | explicit staff finalization, never a migration/background scan\n        v\nFiscalDocument + immutable FiscalSnapshot\n        |\n        | same PostgreSQL transaction\n        v\nFiscalOutboxEvent ---- worker ----> FiscalProviderGateway\n        |                                  |\n        |                                  +--> Mock adapter first\n        |                                  +--> Cloudware adapter later\n        v\nattempt/audit state <---- reconcile ---- provider reference/status\n        |\n        +--> FiscalArtifact metadata ----> private ArtifactStore\n        |\n        +--> additive API projection ----> existing staff/client pages\n```\n\n### 1. Fiscal model seam\n\nIntroduce a separate aggregate linked to `invoices.id`, rather than expanding `Invoice` into a provider payload.\n\nSuggested provider-neutral concepts:\n\n- `FiscalDocument`: internal ID, source invoice ID, document kind, provider key, connection ID, lifecycle state, immutable snapshot version, provider reference/number, issue timestamps, last error classification, and audit timestamps.\n- `FiscalSnapshot`: issuer identity, customer identity, billing address, currency, line items, tax rates/categories/exemption reasons, net/tax/gross totals, rounding data, and source references captured at finalization time.\n- `FiscalAttempt`: attempt number, stable idempotency/correlation key, request/response metadata with secrets and unnecessary personal data redacted, outcome class, and timestamps.\n- `FiscalArtifact`: fiscal document ID, artifact kind (for example provider PDF), storage key, media type, size, checksum, provider version/reference, and creation time.\n\nBoundaries:\n\n- The snapshot is provider-neutral and immutable after finalization.\n- Provider-specific payloads and response details stay in adapter code or redacted attempt metadata, not in `Invoice`.\n- Provider fiscal state is distinct from operational `Invoice.Status`.\n- A unique constraint should prevent more than one active issuance aggregate for the same source invoice/document intent. Corrections or credit documents must be explicit related documents, not a hidden retry.\n- Existing rows receive no outbox event during migration. A new explicit eligibility/finalization marker or a newly created `FiscalDocument` is the only queue entry condition.\n\n### 2. Provider gateway seam\n\nDefine the application-facing port around business operations, not Cloudware HTTP routes. A minimal shape is:\n\n- verify/use a named provider connection;\n- issue a canonical fiscal snapshot using a stable internal idempotency key;\n- query/reconcile by provider reference and, where supported, idempotency/correlation key;\n- retrieve artifact metadata/content when provider delivery requires it;\n- expose normalized error classes: validation/rejected, unauthorized/connection-expired, rate-limited/transient, ambiguous outcome, and permanent provider failure.\n\nThe selected provider key is persisted on `FiscalDocument` before dispatch and never changes during automatic retry or reconciliation. Another provider may be chosen only for a new, explicit document intent; the system must not fail over an in-flight document automatically.\n\nCloudware-specific OAuth scopes, endpoints, payload mappings, numbering behavior, supported lookup keys, webhooks, and PDF semantics must be filled from the research artifact rather than assumed in proposal/spec.\n\n### 3. Transactional outbox and reconciliation seam\n\nUse a PostgreSQL outbox table written in the same transaction that creates the fiscal document/snapshot. The current Redis queue implementation acknowledges jobs without doing any work and therefore cannot provide delivery guarantees.\n\nRecommended state progression:\n\n```text\noperational draft\n  -> fiscal pending\n  -> dispatching\n  -> issued | rejected | connection_action_required | outcome_unknown\n  -> reconciled issued/rejected\n```\n\nOperational rules:\n\n- Claim outbox work atomically, with lease/lock expiry so a crashed worker can be recovered.\n- Retry only transient technical failures with capped backoff and an attempt limit.\n- Treat timeout/connection loss after request dispatch as `outcome_unknown`; reconcile with the same provider before any resubmission.\n- Never create a new provider request merely because polling cannot confirm the old one.\n- Treat business validation rejection as terminal until an operator corrects the operational draft and explicitly creates a new finalization intent.\n- Record actor, source invoice, provider, correlation/idempotency key, transitions, and redacted failures for audit.\n- Support manual retry/reconcile controls in GonsGarage with authorization and concurrency protection.\n- Keep webhook ingestion optional until official Cloudware evidence confirms it; polling/reconciliation must remain a valid internal seam.\n\nA worker may initially run in the API binary for the single-instance deployment, but the lease-based repository and worker service should not depend on there being only one process. Readiness should distinguish core API/database availability from provider degradation so an external outage does not take down ordinary workshop operations.\n\n### 4. OAuth/provider connection seam\n\nThe application is currently documented as one deployed instance per workshop, and `domain.Workshop` is not a persisted tenant/company aggregate. The first connection model can therefore be instance/workshop-scoped, while retaining a stable connection ID so multi-provider support does not become global environment state.\n\nSuggested connection record:\n\n- internal connection ID and provider key;\n- status such as `disconnected`, `authorizing`, `connected`, `action_required`, `revoked`;\n- provider account/organization reference and granted scopes;\n- encrypted access/refresh credentials, expiry, and key version;\n- created/updated/last-verified timestamps and audit actor;\n- no token values in API responses, logs, outbox payloads, or frontend storage.\n\nUse CSRF-bound OAuth state and PKCE if the provider supports/requires it; exact protocol behavior is research-dependent. Encryption requires a dedicated production secret/key and rotation strategy—JWT defaults or plaintext database storage are not acceptable. Integration connection management should be manager/admin-only even if all workshop staff may be allowed to issue documents.\n\n“Operators never open Cloudware” is achievable for normal issuance and reconciliation. Product must clarify whether a manager/admin may be redirected to Cloudware once for OAuth consent, because OAuth authorization normally requires provider-hosted user interaction.\n\n### 5. PDF artifact seam\n\nThe existing generic `FileStorage` port and `domain.File` model have no content stream, media type, storage key, checksum, authorization context, or implementation. Avoid forcing fiscal PDFs through that incomplete abstraction.\n\nIntroduce a narrow private `FiscalArtifactStore` port or first evolve storage explicitly. Store immutable metadata in PostgreSQL and binary content in a configurable private backend (local mounted volume for development/mock, durable object storage or equivalent for production). Never expose provider bearer URLs or credentials.\n\nServe artifacts through authenticated GonsGarage endpoints that reuse invoice authorization:\n\n- staff can access fiscal artifacts according to the invoice staff policy;\n- clients can access artifacts only for invoices whose `customerId` is their user ID;\n- responses use a safe filename, correct PDF media type, and content disposition;\n- checksum and provider reference permit audit/reconciliation.\n\nThe authority/retention decision remains open: either archive the provider PDF at issuance and serve that immutable copy, or retrieve from the provider and cache. The first option is operationally safer but creates backup, retention, and privacy obligations.\n\n### 6. Transparent UI seam\n\nKeep the existing routes and page hierarchy:\n\n- Staff: extend `/accounting/issued-invoices` list/detail with provider-neutral fiscal badges and actions such as `Emitir documento fiscal`, `Tentar novamente`, `Reconciliar`, and `Descarregar PDF` where state permits.\n- Client: extend `/my-invoices` list/detail with a simple finalized/pending/unavailable presentation and in-app PDF download; never show provider credentials or require a Cloudware account.\n- Connection setup: add a separate manager/admin integration-settings surface. Normal invoice operators stay within the invoice page.\n\nDo not overload the current editable `Estado` input with provider state. Before finalization, show missing fiscal-readiness fields. During asynchronous issuance, show a durable pending state and allow refresh without duplicate submissions. After issuance, make immutable fiscal facts and the official artifact recognizable while preserving client notes editing.\n\n## Mock-provider foundation before credentials\n\nA useful credential-free foundation is a deterministic adapter implementing the same gateway port as Cloudware. It should not imitate undocumented Cloudware JSON; it should exercise normalized application behavior.\n\nMinimum scenarios:\n\n1. Successful issuance returns a stable mock provider reference and deterministic PDF bytes.\n2. Repeated calls with the same idempotency key return the same document, not a duplicate.\n3. Validation rejection returns structured field/business errors.\n4. Unauthorized/expired connection moves the connection/document to action-required without retry loops.\n5. Transient failure retries with backoff.\n6. Ambiguous timeout records unknown outcome; reconciliation later resolves it without blind reissue.\n7. Concurrent worker claims issue once.\n8. A configured provider never changes automatically during failure.\n9. Legacy invoices remain untouched unless a staff user explicitly finalizes an eligible draft.\n10. Staff/client artifact authorization follows the current invoice ownership rules.\n\nThe mock can be an in-process adapter selected by configuration for tests/development, backed by deterministic persisted mock results where restart/reconciliation tests require continuity. An optional local HTTP fake is useful later for transport-contract tests, but it is not required to establish the application seam.\n\n## Data gaps that block real fiscal issuance\n\nCurrent models do not contain enough canonical information to form a compliant fiscal request:\n\n- customer tax identifier and structured legal name/address/country;\n- persisted issuer/workshop fiscal profile (the current `Workshop` type is not a real persisted company model);\n- currency and decimal/minor-unit monetary values;\n- invoice line items, quantities, unit prices, tax rates/categories, exemptions, discounts, and rounding;\n- fiscal document kind, series/number intent, issue/due dates, and correction/reference relationships;\n- linkage from an invoice to repair/service-job lines if those are intended as the source;\n- a defined payment-status versus fiscal-document-status distinction.\n\nThese should be added as explicit operational inputs and then copied into the immutable snapshot. Looking up mutable `User` fields at retry time would make retries non-deterministic and is not acceptable.\n\n## Product decisions required before proposal\n\n### Blocking decisions\n\n1. **Finalization trigger:** Is fiscal issuance an explicit staff action, or does a new operational status transition enqueue it automatically? Recommendation: explicit `Emitir` action for the first release.\n2. **Legacy boundary:** What makes a post-rollout draft eligible? Recommendation: migration defaults all existing rows to not eligible; only a new explicit fiscal draft/version marker can be finalized. Never infer eligibility from `createdAt` alone.\n3. **Edit/delete policy:** What may staff change or delete after pending/issued/rejected states? Recommendation: freeze the fiscal snapshot at pending, reject delete for pending/issued, and use explicit corrective documents instead of mutation.\n4. **Fiscal input model:** Are invoice lines entered independently, derived from service-job/repair work, or both? Decide tax-inclusive/exclusive pricing, supported currency, discounts, rounding, tax rates, and exemption reasons.\n5. **Customer identity:** Which fields are mandatory for consumer versus business customers, and may staff override the customer master for one invoice before finalization?\n6. **Issuer profile:** Where are workshop legal name, tax ID, address, tax regime, default series, and related settings managed in this single-workshop deployment?\n7. **Document lifecycle:** Which document types are in the first release (invoice only versus invoice-receipt, simplified invoice, credit note, cancellation), and what is the legal correction flow?\n8. **Roles:** May all `employee|manager|admin` roles issue/retry/reconcile, or only manager/admin? Recommendation: connection management manager/admin-only; issuance permission must be explicitly selected.\n9. **Completion semantics:** Is the operator action asynchronous (`202/pending`) or does the UI wait briefly for a result? Recommendation: durable asynchronous state even if the first attempt is fast.\n10. **PDF authority and retention:** Archive provider PDF at issuance or fetch on demand; define retention, backup, and access logging.\n11. **OAuth consent:** Who connects/reconnects the provider, and is a one-time redirect to Cloudware acceptable for that administrator despite the no-Cloudware operator rule?\n12. **Rollout mode:** Will mock mode be permitted only outside production, or may production run with fiscal controls disabled until Cloudware is connected? Mock output must never be presented as a legal fiscal document.\n\n### Research-dependent decisions\n\nThe proposal must consume the separate official Cloudware evidence before fixing:\n\n- OAuth grant, PKCE/state requirements, refresh/revocation behavior, scopes, and account ownership;\n- issuance endpoint semantics, required document/customer/tax fields, numbering/series ownership, and supported document types;\n- provider idempotency and lookup/reconciliation capabilities;\n- webhook availability, signatures, ordering, and retry rules;\n- error taxonomy, rate limits, timeout guidance, sandbox behavior, and credential availability;\n- PDF availability, authenticity, retention, download lifetime, and whether Cloudware or GonsGarage is authoritative;\n- cancellation/credit-note workflow and legal immutability requirements.\n\n## Delivery and review risk\n\nThe complete foundation crosses domain models, migrations, transaction handling, worker lifecycle, security/credential storage, provider adapters, handlers, frontend types/services/pages, and backend/frontend tests. It is very likely to exceed the confirmed 600-line review budget if implemented as one undivided change.\n\nBefore apply, the parent should obtain a delivery decision under the configured ask-on-risk policy. A reviewable sequence would normally separate: (1) canonical fiscal model + gateway + deterministic mock, (2) transactional outbox/worker/reconciliation, (3) OAuth/Cloudware adapter after research and credentials, and (4) artifact/UI rollout. This is a planning recommendation only; no chain strategy is selected here.\n\n## Risks and mitigations\n\n| Risk | Mitigation |\n|---|---|\n| Duplicate legal documents after timeout/retry | Stable internal idempotency key, unique constraints, unknown-outcome state, and same-provider reconciliation before resubmission. |\n| Accidental fiscalization of historical rows | No migration-created events; explicit eligibility/finalization only; migration default false for every existing row. |\n| Provider lock-in | Canonical snapshot and normalized gateway/errors; Cloudware types remain inside its adapter. |\n| Mutable operational data alters a legal document | Immutable snapshot captured once; provider payload generated only from that snapshot. |\n| OAuth credential disclosure | Encrypted server-side storage, dedicated key, redacted logs/events, admin-only connection APIs, no frontend tokens. |\n| Provider outage blocks garage operations | Asynchronous outbox; core invoice API remains available; provider health is not core API readiness. |\n| Current delete/update contract conflicts with fiscal immutability | Preserve legacy/draft behavior and add explicit conflict/correction rules for pending or issued documents. |\n| Decimal/tax discrepancies | Canonical decimal or minor-unit model with explicit rounding; retain float only at the legacy compatibility boundary. |\n| PDF loss or unauthorized access | Private artifact store, checksum/metadata, backups, and downloads authorized through existing invoice ownership. |\n| Mock mistaken for legal issuance | Environment guard, visible non-fiscal labeling, and prohibition on mock legal artifacts in production. |\n| Schema drift from startup AutoMigrate | Explicit migration and fail-fast validation for fiscal tables/constraints; do not rely only on startup migration warnings. |\n\n## Recommended proposal posture\n\n**Not ready for a fully committed Cloudware proposal yet.** It is ready for a proposal that explicitly limits itself to the provider-neutral/mock foundation and records the blocking product choices as assumptions or decisions. A Cloudware-enabled proposal must wait for the official research artifact and resolution of finalization, fiscal input, role, immutability/correction, OAuth-consent, and PDF-retention decisions.\n\n## Evidence inspected\n\n- `openspec/config.yaml`\n- `openspec/specs/billing/spec.md`\n- `openspec/specs/invoices/spec.md`\n- `openspec/specs/mvp-role-access/spec.md`\n- `docs/application-analysis.md`\n- `docs/billing-traceability.md`\n- `docs/invoices-traceability.md`\n- `backend/internal/domain/invoice.go`\n- `backend/internal/domain/user.go`\n- `backend/internal/domain/workshop.go`\n- `backend/internal/domain/file.go`\n- `backend/internal/service/invoice/invoice_service.go`\n- `backend/internal/repository/postgres/invoice_repository.go`\n- `backend/internal/handler/invoice_handler.go`\n- `backend/internal/core/ports/repositories.go`\n- `backend/internal/core/ports/services.go`\n- `backend/internal/core/ports/external/file_storage.go`\n- `backend/internal/repository/redis/queue_repository.go`\n- `backend/internal/service/invoice/invoice_service_test.go`\n- `backend/internal/repository/postgres/invoice_repository_test.go`\n- `backend/internal/handler/p1_accounting_routes_test.go`\n- `backend/cmd/api/main.go`\n- `backend/scripts/run_migrations.go`\n- `backend/migrations/010_p1_suppliers_received_invoices_billing_documents.up.sql`\n- `docker-compose.yml`\n- `docker-compose.prod.yml`\n- `frontend/src/types/accounting.ts`\n- `frontend/src/lib/services/issued-invoice.service.ts`\n- `frontend/src/lib/server/my-invoices-initial.ts`\n- `frontend/src/app/accounting/issued-invoices/**`\n- `frontend/src/app/my-invoices/**`\n"
